# Каталог: модель и API (этап 1)

## Модель

- **companies** — компания-покупатель, поставщик или обе роли (`is_buyer`, `is_supplier`, `CHECK` хотя бы одна). Статус `active|suspended`. БИН (12 цифр) обязателен для компаний из кабинета; у ранее созданных строк может отсутствовать.
- **categories** — дерево через `parent_id` (`ON DELETE RESTRICT`). Запрещены собственный родитель (`CHECK`) и циклы (триггер `categories_prevent_cycle`).
- **products** — общая карточка: названия kk/ru, описание, бренд, единица измерения (фиксированный список кодов), характеристики `attributes` (JSONB-массив `{key, name_kk, name_ru, value}`).
- **offers** — предложение поставщика: цена в тиынах (`price_tiyn` — это РРЦ, публичная), остаток, минимальный заказ, доставка. `UNIQUE (product_id, supplier_company_id)`; владельцем может быть только компания с ролью поставщика (триггер `offers_require_supplier`). Будущая корзина ссылается на `offers.id`.

> Правила этапа 3 (публикация только проверенным поставщиком, артикулы, GTIN, уровни цен, упаковка, НДС, отделение демо от настоящих цен) приняты, но **не реализованы**: [decisions/supplier-stage-3.md](decisions/supplier-stage-3.md). Ниже описано текущее поведение.

Демо-строки помечены `is_demo = TRUE` и создаются только командой `seed`.

## Доступное предложение и минимальная цена

Предложение считается **доступным**, если одновременно:

1. `offers.is_active = TRUE`;
2. компания-поставщик `is_supplier = TRUE` и `status = 'active'`;
3. `stock_quantity >= min_order_quantity` — остатка хватает хотя бы на минимальный заказ.

Определение хранится в одном месте: `offers.AvailableCondition` (`backend/internal/offers/model.go`).

- `min_price` товара = `MIN(price_tiyn)` по доступным предложениям; если их нет — `null`.
- `offer_count` = число доступных предложений.
- На странице товара показываются все активные предложения активных поставщиков: сначала доступные (по цене), затем недоступные с пометкой «недостаточно остатка». Поэтому недоступное, но более дешёвое предложение видно, но **не** уменьшает минимальную цену.

## API

Все ответы: `{"data": ...}`; ошибки: `{"error": {"code", "message"}}`.

| Метод | Путь | Описание |
|---|---|---|
| GET | `/api/v1/health` | Процесс жив (БД не проверяется) |
| GET | `/api/v1/ready` | Готовность: ping PostgreSQL, 503 при недоступности |
| GET | `/api/v1/categories/tree` | Дерево активных категорий; `product_count` включает подкатегории |
| GET | `/api/v1/products` | Список с поиском, фильтром, сортировкой, пагинацией |
| GET | `/api/v1/products/:id` | Карточка + `category_path` (хлебные крошки) |
| GET | `/api/v1/products/:id/offers` | Предложения поставщиков; 404 для неизвестного товара, `[]` если предложений нет |

### Параметры `GET /products`

| Параметр | Значения | По умолчанию |
|---|---|---|
| `q` | до 100 символов; делится на слова (≤5), каждое слово должно встретиться в `name_kk`, `name_ru` или `brand` (ILIKE, без учёта регистра, `%`/`_` экранируются) | — |
| `category` | slug; включает **все** вложенные активные подкатегории (рекурсивный CTE). Неизвестный slug → 404 `category_not_found` | — |
| `sort` | `newest`, `price_asc`, `price_desc`, `offers` | `newest` |
| `page` | 1…10000 | 1 |
| `page_size` | 1…48 | 12 |

Сортировка: пользователь выбирает только ключ; текст `ORDER BY` берётся из фиксированной карты `sortClauses`. Все значения передаются параметрами `$n`. При сортировке по цене товары без цены идут последними (`NULLS LAST`); каждая сортировка заканчивается `id` для стабильной пагинации.

Ответ: `{items, page, page_size, total, total_pages}`.

Неактивная категория скрывает себя, всё своё поддерево и его товары.

## Поиск по-казахски

Поиск без учёта регистра (`ILIKE`, `lower()`) зависит от `LC_CTYPE` базы: локаль должна сворачивать регистр кириллицы, включая казахские буквы (Ә, Ғ, Қ, Ң, Ө, Ұ, Ү, Һ, І). Проверенные конфигурации:

| Где | PostgreSQL | Локаль базы | Результат |
|---|---|---|---|
| Production (VPS, `qurylys_b2b`) | 16, Ubuntu 24.04 | `libc`, `C.UTF-8` (glibc) | работает |
| Локальный Docker (`compose.yml`) | 17 | `builtin`, `C.UTF-8` | работает |
| — | 16 на Alpine (musl) | `libc`, `C` | **не работает**: кириллица не сворачивается |

CI прогоняет интеграционные тесты на обеих рабочих конфигурациях. `TestDatabaseCaseFolding` проверяет `lower`/`upper`/`ILIKE` для всего казахского и русского алфавита и первым сообщит о неподходящей локали; `TestSearch` проверяет поиск в обоих регистрах. Пересоздавать production-базу ради другой локали не нужно и нельзя.

Триграммные GIN-индексы (`pg_trgm`) ускоряют `ILIKE '%…%'`.

## Артикул каталога, GTIN и заявки на товары (этап 3, шаги 3.1–3.2)

- `products.catalog_no` (`QB0000001`) назначает база; уникален, неизменяем, возможны пропуски. Это не артикул продавца.
- `products.gtin` — только подтверждённый, 14 знаков, с источником и датой. У старых и демо-карточек пуст, `needs_review = TRUE`.
- Заявка: черновик → на модерации → нужны исправления / одобрена / отклонена. Отправка — с заявленным GTIN; одобрение — только с подтверждённым. Одобрение создаёт карточку **без** предложения. Смена GTIN снимает подтверждение. На проверке заявка заблокирована триггером.
- Подаёт владелец компании-поставщика. Модератор — держатель `catalog.moderate` без конфликта интересов (не автор, не член и не бывший член). Решение привязано к `submission_no`, строка компании блокируется.
- Журналы: `catalog_events` (только добавление) и `audit_events`.

| Метод и путь | Кто |
|---|---|
| GET, POST `/companies/:id/catalog-requests`; GET, PUT `/:requestId`; POST `/:requestId/submit` | владелец (изменение — при направлении «Поставщик») |
| GET `/catalog/moderation/requests`, `/:id`; POST `/:id/gtin`, `/:id/decision` | `catalog.moderate` |
| PUT `/admin/users/:id/catalog-moderate` `{enabled}` | администратор |

Отчёт перед внедрением, только чтение, без персональных данных, работает на схеме 8 и новее: `admin catalog-report`.

## Предложения поставщика (этап 3, шаг 3.3)

- `offers.owner_state` — выбор владельца: `draft` / `published` / `hidden`. **Это не публичный показ:** публичные запросы по-прежнему читают `is_active`, который у настоящих предложений всегда FALSE (CHECK). Показ — шаг 3.4.
- Условия публикации — единственное определение `selleroffers.reasonsSQL`; невыполненные возвращаются в `reasons`.
- РРЦ: `price_tiyn`, `min_order_quantity`, `retail_sale_mode`, `retail_step`. Опт и крупный опт — `offer_price_tiers`, публичные запросы её не читают.
- Правило количества — `sale_rule_ok` (SQL), `quantity.SaleRuleOK` (Go): минимум кратен шагу; упаковками шаг кратен упаковке; поштучно у штучных единиц шаг 1. Штучные: `piece, bag, pack, roll, sheet, pallet`, только целые.
- Сумма — `quantity.Total` (Go), `round(numeric)` (SQL), `lineTotal` (браузер): half-up один раз, без `float`. Меняются вместе.
- Одно предложение на карточку; `seller_sku` уникален в компании без учёта регистра; `version` — оптимистичная блокировка. Журнал `offer_events` содержит закрытые цены, `audit_events` — нет.
- Смешать демо и настоящее нельзя; `is_demo` неизменяем; единица и GTIN карточки с предложениями закрыты.

| Метод и путь | Кто |
|---|---|
| GET `/companies/:id/offers`, `/:offerId` | владелец и сотрудник |
| GET `/companies/:id/offer-cards?q=` | владелец |
| POST `/companies/:id/offers`; PUT `/:offerId`; POST `/:offerId/publish`, `/hide` (с `version`) | владелец; MRX без членства — 403, остальные посторонние — 404 |

## Администрирование каталога (задача 28.11.2026, часть шага 3.5)

Решения — [8б в decisions](decisions/supplier-stage-3.md). Миграция [00011](../backend/migrations/00011_admin_catalog.sql) только расширяет схему: ID, связи и тексты брендов не меняются.

**Навигация.** «Администрирование»: Пользователи, Сотрудники платформы, Сотрудники компаний (только `admin`), Категории, Бренды, Товары. Администратор видит разделы каталога всегда; без разрешения раздел объясняет причину и ведёт на его страницу пользователя, где право выдаётся явно. Держатель разрешения без роли `admin` видит только свои разделы. Компания и активная компания для управления каталогом не нужны.

**Права.** Три независимых разрешения в `platform_permissions`, выдаёт и снимает администратор (`PUT /admin/users/:id/permissions/:permission`), всё в `audit_events`. Ни `admin`, ни `mrx` их не дают; каждое проверяется повторно в транзакции действия.

| Разрешение | Что даёт |
|---|---|
| `catalog.moderate` | заявки (как раньше), административный список и карточка товара, создание карточки, правка, подтверждение GTIN, блокировка; чтение справочника брендов |
| `catalog.categories` | дерево категорий |
| `catalog.brands` | справочник брендов и привязка старых текстов |

**Категории** (`internal/categories`). Создание корня и подкатегории, названия KK/RU, порядок, перенос. Адрес (`slug`) задаётся один раз. Цикл и перенос под себя или потомка — 409 `category_cycle` (проверка в API под рекомендательной блокировкой дерева и триггер). Удаление — только без подкатегорий, карточек (любых, включая демо) и заявок; причина в коде ошибки. Правил полей «срок годности / партия» по категориям нет — это шаг 3.6 (BR-11).

**Бренды** (`internal/brands`, таблица `brands`). Название без лишних пробелов, уникально без учёта регистра. `products.brand` остаётся текстом, который читают публичные страницы и поиск: у привязанной карточки он равен названию бренда (триггер, в том числе при переименовании), у непривязанной — прежний текст. Миграция ничего не привязывает. Список «непривязанных текстов» показывает точные тексты настоящих карточек и подсказку-совпадение; привязка — явное действие по точному тексту, прежний текст записывается в журнал карточки. Используемый бренд не удаляется. Демо-карточки не привязываются (CHECK). При одобрении заявки карточка получает бренд, если текст совпадает с названием с точностью до регистра и пробелов.

**Карточки** (`internal/cards`). Цены, остатки и `seller_sku` не читаются и не меняются; видно только число предложений по состояниям.

- Поиск: название, артикул каталога, GTIN (в любой длине). Фильтры: категория с подкатегориями, бренд или «без бренда», состояние (требует проверки, проверена, заблокирована, без GTIN, настоящие, демо).
- Создание: категория, названия, описание, бренд, единица и **подтверждённый GTIN с источником**; артикул назначает база, `needs_review = FALSE`.
- Правка: обязательная причина, `version`, старое и новое — в `catalog_events` (`card_edited`) и `audit_events`. Без настоящих предложений — исправление любых полей. С предложениями — только косметика (N3): категория, единица, GTIN и уже назначенный бренд закрыты (API и триггер `products_linked_guard`), числа в названиях менять нельзя (`card_identity_change`).
- GTIN: подтверждение с источником и `needs_review = FALSE`; дубль — 409 `gtin_exists`; у карточки с предложениями GTIN не меняется. Старым карточкам GTIN не придумывается: только по источнику.
- Блокировка (R6): причина обязательна. Заблокированная карточка — 404 на публичных страницах, вне списка, поиска и счётчиков категорий; новое предложение на неё не создаётся, существующее не публикуется (причина `card_blocked`). Предложения не удаляются, выбор владельца не меняется.
- Конфликт интересов: модератор, который состоит или состоял в компании с настоящим предложением на карточке или в компании заявки, создавшей карточку, видит её, но не действует (403 `conflict_of_interest`).
- Демо-карточки — только чтение (`card_demo`): их ведёт seed.
