# Проверка компаний (этап 2)

Одобрение фиксирует результат проверки и пока ничего не открывает: цены, товары и заказы от него не зависят. На этапе 3 от него будет зависеть публикация предложений ([решения](decisions/supplier-stage-3.md), S1, C8, C10; не реализовано).

## Статусы

```
draft ──► in_review ──► approved
             │  ▲  └──► rejected ──► новая заявка
             ▼  │
        needs_changes
```

Статус компании — представление `company_verification`: `none`, `draft`, `in_review`, `needs_changes`, `approved`, `rejected`, `reverification` (была одобрена, ключевые реквизиты изменились). Открытая заявка у компании одна.

**Ключевые реквизиты:** название, БИН, юридический адрес, представитель, добавление роли поставщика. На проверке их менять нельзя (409). После одобрения изменение снимает статус «Проверена»; возврат прежнего значения его не восстанавливает. Город, телефон и фактический адрес на статус не влияют.

## Кто что может

- **Владелец:** создаёт черновик, загружает и удаляет документы, отправляет, видит документы.
- **Сотрудник:** видит статус, реквизиты, замечания и историю; документов не видит.
- **MRX:** видит отправленные заявки (не черновики), реквизиты и файлы ровно той отправки, решает. Не видит и не решает заявки компаний, где состоит **или состоял**, либо действовал от её имени. Реквизиты, товары и цены менять не может.
- **Администратор** без роли MRX заявок не видит; выдаёт и снимает MRX.

Компания видит «Проверяющий MRX» без имени; проверяющие видят имена.

## Целостность решений

- Решение содержит `submission_no`: нельзя одобрить не ту версию, что открыта на экране.
- Строка компании блокируется (`FOR UPDATE`), затем заново проверяются роль, конфликт интересов, статус и номер отправки. Из одновременных решений проходит одно, остальные — 409.
- Реквизиты на момент отправки — в `snapshot`, хэши документов — в истории.
- `verification_events` — кто, когда, что и почему; изменение и удаление запрещены триггером.
- Триггеры БД: допустимые переходы, обязательный комментарий, «Проверена» только при одобренной заявке этой компании, снятие при смене ключевых реквизитов.

## Документы

- PDF, JPEG, PNG до 5 МБ; до 10 в отправке, до 40 за заявку с учётом заменённых. Тип определяется по содержимому, не по имени.
- Хранятся в PostgreSQL (`verification_documents.data`), попадают в обычную резервную копию. Публичных адресов нет: только через API с проверкой прав, всегда как скачивание (`attachment`, `nosniff`, CSP `sandbox`, `no-store`).
- Файл, который не отправлялся, удаляется физически. Отправленный и затем убранный скрывается, но хранится для истории решений.

## Уведомления

После решения владельцам с подтверждённым email уходит письмо на kk и ru без названия компании, комментария, документов и ссылок. Ошибка почты решение не отменяет.

## API

| Метод и путь | Кто |
|---|---|
| GET `/companies/:id/verification` | член компании |
| POST `/companies/:id/verification`, `/submit` | владелец |
| POST `/companies/:id/verification/documents?kind=registration\|authority\|other` (multipart, поле `file`) | владелец |
| GET, DELETE `/companies/:id/verification/documents/:docId` | владелец |
| GET `/mrx/requests?status=&page=`, `/mrx/requests/:id`, `/mrx/requests/:id/documents/:docId` | MRX |
| POST `/mrx/requests/:id/decision` `{decision: approve\|request_changes\|reject, comment, submission_no}` | MRX |

## Публикация

1. **Nginx на VPS:** в `location /api/` HTTPS-сайта нужен `client_max_body_size 6m;` (добавлено 25.11.2026). Без него файлы больше 2 МБ получат 413.
2. Миграция 00008 только добавляет объекты (схема 7 → 8). Обычный откат на прежний образ отклонится по метке схемы, нужен `rollback --force-schema`.
3. Если роль API отличается от роли миграций: права на новые таблицы **и на представление** `company_verification` (`SELECT`). Без них кабинет ответит 500, а `/ready` — 200.
4. Следить за размером базы и копий: до 50 МБ на отправку.

## Ограничения

Нет антивируса, MFA, срока хранения и удаления документов по запросу, уведомлений MRX о новых заявках, отзыва одобрения и отзыва заявки владельцем.
